# Hylme Pipeline

ระบบรวมข้อมูลขายของ Hylme — อ่านไฟล์ Excel จาก Pancake / MyCloud / Marketplace
แล้วเขียนลงฐานข้อมูลกลางหนึ่งที่ พร้อมสร้างไฟล์ให้ MyCloud · แดชบอร์ด · ทีมเทเลเซล · โมเดล

> **สรุปสั้นที่สุด**
> 1. วางไฟล์ `.xlsx` ลงในโฟลเดอร์ `data/raw/`
> 2. เปิด Terminal ที่โฟลเดอร์ `hylme_pipeline`
> 3. พิมพ์ `python daily_pipeline.py`
> 4. ไฟล์ผลลัพธ์อยู่ใน `data/output/`

## 3 · ติดตั้งครั้งเดียว

```

```

ควรได้ `Python 3.10.x` หรือสูงกว่า

- ถ้าขึ้น **'python' is not recognized** = ยังไม่ได้ติดตั้ง Python หรือไม่ได้ใส่ใน PATH

## 5 · งานประจำวัน

### ไฟล์ที่ pipeline อ่านได้ 7 ชนิด

**ใช้ทุกวัน**

| ไฟล์ | มาจากไหน | ใช้ทำอะไร |
|---|---|---|
| Pancake export | Pancake > ออเดอร์ | ออเดอร์ · สินค้า · ลูกค้า |
| MyCloud outbound-orders | MyCloud > รายงาน | ออเดอร์ marketplace · สถานะจัดส่ง · ทะเบียนยกเลิก (อ่านรอบเดียวได้ครบ 3 อย่าง) |
| `pages_statistics_page_*.xlsx` | **Pancake > สถิติ > สถิติหน้า** | **ลูกค้าใหม่ = ตัวหารของ Conversion Rate** |
| ออเดอร์ยกเลิก / ไม่ได้จัดส่ง | ทีมทำเอง | ทะเบียนยกเลิกที่ระบุยอดเงินจริง |

**ใช้ตอนดึงข้อมูลย้อนหลัง (โหลดครั้งเดียวก็พอ)**

| ไฟล์ | ช่วงข้อมูล | หมายเหตุ |
|---|---|---|
| `รายงานขายฮีลมี 2569.xlsx` | ม.ค. – มิ.ย. 2026 | ยอดที่รายงานไว้ ใช้เป็นตัวเทียบตอนกระทบยอด **ไม่ใช่ยอดดิบ** |
| GoSell export | พ.ย. 2025 – พ.ค. 2026 | ยอดดิบของช่วงนั้น |
| Google Sheet เก่า (1 ไฟล์ = 1 เดือน ชีตชื่อ 1–31) | มิ.ย. – 23 ก.ค. 2026 | ยอดดิบของช่วงนั้น |

วางชนิดไหนก็ได้ปนกันใน `data/raw/` — ระบบดูจากเนื้อไฟล์เอง ไม่ได้ดูจากชื่อไฟล์
**ยกเว้นไฟล์ Google Sheet เก่า** ที่ต้องดูชื่อไฟล์ เพราะไฟล์ไม่ได้เก็บเดือน/ปีไว้ข้างใน
ตั้งชื่อให้มี **ชื่อเดือนไทย + ปี พ.ศ.** เช่น `ยอดขาย มิถุนายน 2569.xlsx` (กติกาเดียวกับของเดิม)

> **โหลดข้อมูลย้อนหลังให้ครบทีละเดือน** ถ้าโหลดมาครึ่งเดือน ออเดอร์ไม่กี่ใบที่มีจะถูกดันให้พอง
> เพื่อให้ยอดรวมเท่าเป้าในรายงาน มีกันชนไว้แล้วแต่ตอนนี้ปิดอยู่ (`calibration_max_ratio: 0`
> ใน `config/revenue_rules.json`) เพื่อให้ยอด ม.ค.–มิ.ย. ตรงรายงานเป๊ะ
> ถ้าจะโหลดย้อนหลังทีละบางส่วน ให้ตั้งกลับเป็น `5.0` ก่อน

> **ไฟล์ Google Sheet เก่ากันซ้ำด้วย "วันที่" ไม่ใช่เลขที่ออเดอร์** โหลดไฟล์เดือนเดิมซ้ำ
> ระบบจะลบของวันที่อยู่ในไฟล์ใหม่ทิ้งก่อนแล้วเขียนใหม่ วันอื่นและไฟล์ระบบอื่นไม่ถูกแตะ
> (เพราะเลข `OLD-...` เป็นลำดับที่เลื่อนได้ทุกครั้งที่แปลง — กติกาเดียวกับของเดิม)

> **สถิติหน้า — ถ้าอยากได้ Conversion แยกรายเพจ × รายวัน ให้ export ทีละเพจ**
> ไฟล์ที่รวมหลายเพจจะแยกรายเพจต่อวันไม่ได้ ระบบจะรวมเป็นก้อน "รวมหลายเพจ" ให้แทน
> และถ้าไฟล์สองไฟล์ครอบคลุม (วัน × เพจ) เดียวกัน ระบบจะใช้ไฟล์ที่ละเอียดกว่าไฟล์เดียว
> อีกไฟล์ถูกข้ามทั้งไฟล์ เพื่อไม่ให้นับซ้ำ (กติกาเดียวกับ `collectPageStat` ของเดิม)

### รอบเช้า — ก่อนส่งของ

1. Export ออเดอร์เมื่อวานจาก Pancake ออกมาเป็น `.xlsx`
2. ลากไฟล์นั้นไปวางใน `hylme_pipeline\data\raw\`
3. เปิด Terminal ที่ `hylme_pipeline` แล้วพิมพ์:

   ```
   python daily_pipeline.py
   ```

4. อ่านรายงานที่ขึ้นบนจอ ดูบรรทัด `[ ! ]` ว่ามีอะไรต้องแก้ไหม
5. เอาไฟล์ `data\output\hylme_MC_export_<วันที่>.xlsx` ไปอัปเข้า MyCloud

### รอบบ่าย — หลัง MyCloud จัดส่งเสร็จ

1. Export ไฟล์ outbound-orders จาก MyCloud
2. Export ออเดอร์ Shopee / Lazada / TikTok (ถ้ามีแยกไฟล์)
3. วางทุกไฟล์ใน `data\raw\` เหมือนเดิม
4. พิมพ์:

   ```
   python update_delivery.py
   ```

5. แดชบอร์ด คิวโทร และข้อมูลโมเดล จะถูกสร้างใหม่ให้อัตโนมัติ

### ถ้าอยากให้เครื่องคำนวณคิวโทรเดิมทำงานต่อท้ายด้วย

```
python daily_pipeline.py --rebuild-engine
```

จะเรียก `hylme_engine/04_rebuild.py` ให้คำนวณ RFM · รอบซื้อซ้ำ · คิวโทร ใหม่จากข้อมูลล่าสุด
โดยไม่ต้อง export ไฟล์ไปวางในโฟลเดอร์ engine เองอีก

| `--dry-run` | อ่านไฟล์และรายงานผล แต่ **ไม่เขียนอะไรลงฐานข้อมูล** ใช้ดูก่อนว่าไฟล์อ่านได้ไหม |
| `--no-archive` | ไม่ย้ายไฟล์ที่โหลดแล้วออกจาก `data/raw/` |
| `--recheck-cancels` | คำนวณการจับคู่ออเดอร์ยกเลิกใหม่ทั้งหมด |
| `--validate-days 0` | ตรวจคุณภาพข้อมูลทั้งฐาน (ปกติตรวจแค่ 90 วันล่าสุด) |
| `--mc-from` / `--mc-to` | เลือกช่วงวันที่ของไฟล์ MyCloud เช่น `--mc-from 2026-09-08 --mc-to 2026-09-08` |
| `--rebuild-engine` | สั่งเครื่องคำนวณคิวโทรเดิมทำงานต่อท้าย |

ตัวอย่าง — ลองดูก่อนว่าไฟล์อ่านได้ไหม โดยยังไม่เขียนอะไร:

```
python daily_pipeline.py --dry-run
```

## 7 · รันซ้ำได้ ไม่ต้องกลัว

ระบบนี้เป็น **idempotent** — วางไฟล์เดิมแล้วรันซ้ำกี่รอบ ฐานข้อมูลก็เหมือนเดิมเป๊ะ

ทดสอบแล้วกับไฟล์ MyCloud จริง (2,099 แถว): รันรอบที่ 2 ได้จำนวนแถว ยอดรวม
และค่า hash ของทั้งตาราง `orders` กับ `order_items` เท่ากับรอบแรกทุกตัว

เพราะทุกการเขียนใช้คีย์หลักทับของเดิม ไม่ใช่การเพิ่มแถวใหม่:

| ข้อมูล | คีย์ |
|---|---|
| ออเดอร์ | `order_id` |
| บรรทัดสินค้า | `order_id` + ลำดับบรรทัด (ลบของเดิมทั้งชุดแล้วเขียนใหม่) |
| เลขอ้างอิงระบบต้นทาง | `system` + `external_id` |
| ทะเบียนยกเลิก | `cancel_key` |
| เหตุการณ์จัดส่ง | `order_id` + วันที่ + สถานะ |

ระบบยังจำ "ลายนิ้วมือ" ของทุกไฟล์ที่เคยโหลด (SHA-256 ของเนื้อไฟล์ ไม่ใช่ชื่อไฟล์)
ถ้าวางไฟล์เดิมซ้ำ รายงานจะบอกว่า **"ไฟล์นี้เคยโหลดแล้ว — ข้อมูลจะไม่เพิ่ม"**

นอกจากนี้ ก่อนเขียนครั้งแรกของแต่ละวัน ระบบจะ **สำรองฐานข้อมูล** ไว้ให้อัตโนมัติ
เป็นไฟล์ `hylme.backup-<วันที่>.db` ข้าง ๆ ตัวจริง

  [ .. ]   ข้อมูลประกอบเฉย ๆ

รายงานฉบับเต็มถูกบันทึกไว้ที่ `data\output\run_report_<วันที่>.txt` เปิดอ่านย้อนหลังได้

### รายการที่เจอบ่อยและแปลว่าอะไร

| ข้อความ | ความหมาย | ต้องทำอะไร |
|---|---|---|
| `ต้องตรวจก่อนอัปโหลด` | ออเดอร์อยู่ในไฟล์ MyCloud แล้ว แต่ข้อมูลไม่ครบ (ไม่มีที่อยู่ / เบอร์ / ช่องทางขาย) | เปิดไฟล์ `.xlsx` แล้วเติมช่องที่ขาดก่อนอัปเข้า MyCloud |

| `cancel_unmatched` | ออเดอร์ยกเลิกที่หาออเดอร์ต้นทางไม่เจอ | มักเป็นออเดอร์เก่ากว่าช่วงข้อมูลที่มี ถ้าเป็นของใหม่ให้เช็คว่า export ครบไหม |
| `cancel_ambiguous` | มีออเดอร์หลายใบที่วันที่+ยอดเงินตรงกันหมด ระบบไม่กล้าเดา | เลือกเองในฐานข้อมูล (ดูข้อ 10) |
| `สถานะที่ยังไม่รู้จัก` | MyCloud ส่งสถานะที่ระบบยังไม่เคยเห็น ตอนนี้นับเป็นยอดขาย | ถ้าถูกต้องแล้ว เพิ่มชื่อสถานะ (ตัวพิมพ์เล็ก) ลงใน `config/statuses.json` คีย์ `mc_ok_status` |
| `delivery_without_order` | มีข้อมูลการจัดส่ง แต่หาออเดอร์ต้นทางไม่เจอ | ออเดอร์นั้นอาจยังไม่ได้ import — ลอง export Pancake ช่วงนั้นเพิ่ม |

## 10 · รายการที่ต้องตรวจ — `validation_review.py`

ระบบตรวจข้อมูลทุกรอบและเก็บผลไว้เป็น "ทะเบียนปัญหา" ปัญหาหนึ่งอันมีแถวเดียวตลอดชีวิต
ไม่ใช่แถวใหม่ทุกวัน จึงจำได้ว่าอันไหนเคยดูแล้ว

### ปัญหาถูกแบ่งเป็นสองพวก

| | คืออะไร | ระบบทำยังไง |
|---|---|---|
| **ข้อมูลปัจจุบัน** | ออเดอร์จากระบบที่ยังใช้อยู่ — Pancake · MyCloud · Marketplace | เตือนตามปกติ เพราะยังตามไปแก้ต้นทางได้ |
| **ข้อมูลเก่า** | ออเดอร์จากระบบที่ปิดไปแล้ว — GoSell (หยุด 18 มิ.ย.) · Google Sheet (หยุด 31 ก.ค.) · ลีด `L0000...` (หยุด 23 ก.ค.) | เก็บไว้ใน audit เฉย ๆ ไม่ขึ้นเป็นงานค้าง |

ดูจาก **ต้นทางของออเดอร์** (`orders.source`) เทียบกับลิสต์ `live_sources` ใน
`config/validation.json` ถ้าวันหนึ่งเลิกใช้ Pancake หรือเพิ่มระบบใหม่ ให้แก้ที่ลิสต์นี้

> **ไม่มีกฎข้อไหนถูกปิด** ทุกกฎยังตรวจครบเหมือนเดิม ถ้า Pancake มีปัญหาแบบเดียวกับที่
> GoSell เคยมี จะขึ้นเตือนทันที — เปลี่ยนแค่ว่าอันไหนถูกยกขึ้นมาเป็นงานที่ต้องทำ

### สถานะของปัญหา

| สถานะ | แปลว่า | ขึ้นเตือนไหม |
|---|---|---|
| `NEW` | เพิ่งเจอ ยังไม่ได้ดู | **ขึ้น** |
| `REVIEWED` | ดูแล้ว รู้แล้วว่าคืออะไร ยังไม่ได้แก้ | ไม่ขึ้น |
| `IGNORED` | สั่งว่าไม่ต้องเตือนอีก | ไม่ขึ้น |
| `RESOLVED` | หายไปจากผลตรวจแล้ว — ระบบตั้งให้เอง | ไม่ขึ้น |

ระบบ **ไม่เคยเขียนทับสถานะที่ตั้งเอง** ตั้ง `REVIEWED` ไว้ รันอีกกี่รอบก็ยัง `REVIEWED`
ยกเว้นกรณีเดียว: ปัญหาที่ปิดไปแล้ว (`RESOLVED`) กลับมาเจออีก จะเด้งกลับเป็น `NEW`
เพราะของจริงกลับมาแล้ว ส่วน `IGNORED` ระบบไม่แตะเลยไม่ว่าอะไรจะเกิดขึ้น

### คำสั่งที่ใช้บ่อย

```
python validation_review.py                       ดูว่าต้องตรวจอะไรบ้าง
python validation_review.py --summary             เอาแค่ตัวเลขสรุป
python validation_review.py --rule missing_sku    เจาะกฎเดียว
python validation_review.py --scope historical    ดูข้อมูลเก่าที่เก็บไว้ใน audit
python validation_review.py --export              สร้างไฟล์ .xlsx + .csv
```

ตั้งสถานะ — ใส่ `--note` ไว้เสมอ จะได้รู้ทีหลังว่าทำไมถึงตัดสินใจแบบนั้น

```
python validation_review.py --set REVIEWED --rule missing_sku --entity PK-4790 --note "รอ SKU ใหม่"
python validation_review.py --set IGNORED  --rule missing_customer --scope current --note "marketplace ปิดเบอร์เป็นปกติ"
```

ถ้าเปลี่ยนทีละหลายรายการ ระบบจะสรุปให้ดูก่อนแล้วถามยืนยัน (ใส่ `--yes` เพื่อข้ามการถาม)

### ไฟล์รายการที่ต้องแก้

ทุกรอบที่รัน `daily_pipeline.py` จะได้ไฟล์นี้ให้ไล่แก้

```
data/output/validation_issues_YYYY-MM-DD.xlsx
data/output/validation_issues_YYYY-MM-DD.csv
```

มีเฉพาะรายการที่ต้องลงมือจริง (ข้อมูลปัจจุบัน + ยังไม่ได้ดู) ในไฟล์ไม่มีชื่อ เบอร์ หรือที่อยู่ลูกค้า
มีแค่เลขที่ออเดอร์กับต้นทาง

### ประวัติยังอยู่ครบ

ตาราง `validation_log` เก็บผลตรวจของทุกรอบเหมือนเดิม ไม่มีการลบ ทะเบียนสถานะเป็นตารางใหม่
คนละตัวกัน ค้นย้อนหลังได้ว่ารอบไหนเจออะไร รวมถึงข้อมูลเก่าที่ถูกจัดเป็น audit-only

## 11 · แก้ผลการจับคู่ออเดอร์ยกเลิกเอง

ระบบจับคู่ให้อัตโนมัติ 6 ชั้น (เลข Lead → เลขแพลตฟอร์ม → เลข MyCloud →
เบอร์+ยอด → ชื่อ+ยอด → วันที่+ยอด) เคสที่มีผู้สมัครหลายรายจะขึ้นเป็น `ambiguous`
และ **ระบบจะไม่เดา** ให้เลือกเอง

**สิ่งที่ต่างจากของเดิม** — ผลการจับคู่ถูกบันทึกไว้ถาวรในตาราง `cancellations`
ของเดิมคำนวณใหม่ทุกครั้ง ทำให้เคสที่เคยชัดเจนกลายเป็นกำกวมได้ในวันถัดมา
เมื่อมีออเดอร์ใหม่ที่วันที่+ยอดเงินตรงกันเข้ามา ตอนนี้จับคู่แล้วคือจบ

ถ้าจะเลือกเอง เปิดฐานข้อมูลด้วย [DB Browser for SQLite](https://sqlitebrowser.org/)
(ฟรี ใช้เมาส์คลิกได้ ไม่ต้องพิมพ์คำสั่ง) แล้วแก้ในตาราง `cancellations`:

- `order_id` = ใส่เลขออเดอร์ที่ถูกต้อง
- `match_status` = `matched`
- `confirmed_by` = ชื่อคุณ (ใส่ชื่อไว้แล้ว `--recheck-cancels` จะไม่ลบทิ้ง)

## 12 · เจอ error แล้วทำยังไง

**อ่านบรรทัดสุดท้ายก่อนเสมอ** — Python เขียนสาเหตุจริงไว้บรรทัดล่างสุด

| ข้อความ | สาเหตุ | วิธีแก้ |
|---|---|---|
| `'python' is not recognized` | ยังไม่ได้ติดตั้ง Python หรือไม่ได้ใส่ใน PATH | ลอง `py` แทน หรือติดตั้งใหม่โดยติ๊ก "Add Python to PATH" |
| `No module named 'openpyxl'` | ยังไม่ได้ติดตั้งไลบรารี | `pip install openpyxl` |
| `No module named 'pipeline'` | เปิด Terminal ผิดโฟลเดอร์ | `cd` เข้าไปที่ `hylme_pipeline` แล้ว `dir` ดูว่าเห็น `daily_pipeline.py` ไหม |
| `ไม่รู้จักรูปแบบไฟล์นี้` | ไฟล์ที่วางไม่ใช่ Pancake / MyCloud / สถิติหน้า / ไฟล์ยกเลิก | ตรวจว่า export ถูกชนิด หรือชีตถูกเปลี่ยนชื่อ |
| `database is locked` | เปิดไฟล์ `.db` ค้างไว้ในโปรแกรมอื่น | ปิด DB Browser แล้วรันใหม่ |
| `Permission denied` ตอนเขียนไฟล์ | ไฟล์ `.xlsx` เปิดค้างอยู่ใน Excel | ปิด Excel แล้วรันใหม่ |

ถ้าเจอข้อความยาว ๆ ที่ขึ้นต้นว่า `Traceback` ให้คัดลอกทั้งก้อนมาถามได้เลย
สคริปต์เขียนไว้ให้พิมพ์ข้อความนี้เมื่อเจอข้อผิดพลาดที่ไม่ได้คาดไว้อยู่แล้ว

## 13 · ทดสอบก่อนใช้จริง (แนะนำให้ทำครั้งแรก)

ทดลองกับ **สำเนา** ฐานข้อมูล ไม่แตะตัวจริง — ตั้ง environment variable `HYLME_DB`:

```
copy ..\hylme_engine\hylme.db %USERPROFILE%\hylme_test.db
set HYLME_DB=%USERPROFILE%\hylme_test.db
python daily_pipeline.py
```

ถ้าผลออกมาถูกต้องแล้ว ปิด Terminal (ค่า `set` จะหายไปเอง) แล้วเปิดใหม่เพื่อรันกับตัวจริง

ในโฟลเดอร์ `data/samples/` มีไฟล์ทดสอบให้แล้ว 2 ไฟล์:

- `pancake_TEST.xlsx` — ออเดอร์ทดสอบ 4 ใบ ครอบคลุมเคสยาก
  (ออเดอร์ 2 สินค้าที่มีรหัสเฉพาะบรรทัดแรก · ออเดอร์แจกฟรี · ออเดอร์ยกเลิก · Olive Oil 1 ขวด)
- `mycloud_07_sample.xlsx` — ไฟล์ MyCloud จริงของเดือน 07

ก๊อปปี้ไปวางใน `data/raw/` แล้วรันดูได้

## 14 · สิ่งที่ยังไม่ได้ทำ (Phase ถัดไป)

| Phase | เนื้อหา | สถานะ |
|---|---|---|
| 0 | ตรวจ repo ที่ตั้งค่าไว้ใน index.html ว่าเป็น public ไหม + เพิกถอน token | **ยังไม่ได้ทำ — ด่วนที่สุด** |
| 1-4 | config · loaders · master data · exports | เสร็จแล้ว |
| 5 | ให้แดชบอร์ดอ่าน `data/output/dashboard/*.json` แทน `EMBEDDED_DATA` | เสร็จแล้ว — `dashboard.html` (ดูข้อ 9.5) |
| — | **กระทบยอดกับรายงานขายฮีลมี 2569** (`DAY_TARGET` / `MKP_TRUTH`) | **ยังไม่ได้ย้าย — ดู `LOGIC_MAP.md` §8.1** |
| 6 | Local API + ปุ่มในแดชบอร์ด แทนการเปิด Terminal | ยังไม่ได้ทำ |
| 7 | ให้ `hylme_scoring_v2_daily.py` อ่านจาก master database โดยตรง | ทำบางส่วน (`--rebuild-engine` ใช้ได้แล้ว) |

> **`LOGIC_MAP.md`** ในโฟลเดอร์นี้คือแผนที่ว่า logic แต่ละข้อของ `index.html` ไปอยู่ไฟล์ไหนฟังก์ชันไหน
> พร้อมเลขบรรทัดอ้างอิง และรายการสิ่งที่ยังไม่ได้ย้าย — อ่าน §8.1 ก่อนเทียบตัวเลขยอดขายใด ๆ

### สิ่งที่ต้องยืนยันก่อนใช้กับข้อมูลจริงทั้งชุด

1. **จำนวนออเดอร์และยอดขายต้องตรงกับแดชบอร์ดเดิม** — วิธีตรวจอยู่ในข้อ 12
   รันกับสำเนา แล้วเทียบตัวเลขในไฟล์ `data/output/dashboard/monthly.json` กับหน้าสรุปรายเดือนของ `index.html`
2. **ออเดอร์ marketplace** — pipeline นี้ตั้ง `order_id` ให้ออเดอร์ marketplace เป็น `MKP-` อย่างเดียว
   ต่างจากของเดิมที่อาจสร้างทั้ง `MC-` และ `MKP-` แล้วค่อยหักล้างกันด้วยการเทียบยอดเงิน
   ตัวเลขควรตรงกัน แต่ต้องเทียบให้เห็นก่อน
3. **สถานะ `SHIP_TO_DROP_POINT` · `WAITING_CONFIRM` · `IN_PROGRESS`** จากไฟล์ MyCloud
   ตอนนี้นับเป็นยอดขาย (เหมือนของเดิม เพราะไม่เข้าเงื่อนไขยกเลิก) — ยืนยันว่าถูกต้องไหม
